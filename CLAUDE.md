# SID Song Crafter Project Guide

This file is the canonical contributor and agent guide; [AGENTS.md](AGENTS.md) is a relative symlink to [CLAUDE.md](CLAUDE.md). Edit this file to update both entry points. ## Retrieve before researching

The established master-composer studies are the primary repertoire and carry the strongest influence on sound and arrangement choices. Popular-song and BASIC interpretations provide supporting, context-specific evidence; they do not displace the masters merely because a patch is convenient or liked once. Expand master references when a concrete gap calls for contrasting evidence, while retaining each source’s execution and listening limits.

Before SID technique explanations, arrangement, sound design or listening-feedback changes, start with the [technique lookup](docs/research/technique-index.md), then read the relevant owning study and reusable example. Search locally before new research. Choose methods by musical purpose and model, timing, voice and filter constraints; check their listening verdict before reuse. Retain useful decisions in the existing study or recipe documentation. Repair missing index routes or aliases.

For every stereo arrangement, apply the [SID hardware and mixing contract](docs/research/sid/dual-sid.md#plan-the-sound-hardware-and-the-mix-together) before assigning parts. Each chip has three voices but one mono output, shared filter/master volume and same-chip oscillator dependencies; there is no per-voice pan register. Record musical role → chip/voice → coupling/filter ownership → output matrix. Choose positions deliberately by musical role before allocating chips: a central lead may share the center with bass or other parts when musically justified. Do not mistake chip grouping for an intended placement map, or turn a centered-lead request into a rule that nothing else may be centered. Distinguish native PSID behavior from the listening WAV's mixer settings, and three-part redistribution from use of six voices for additional musical roles. Keep these constraints in the reusable workflow and executable checks, not only in the conversation.

## Preserve sources and SID expression

Retain originals, provenance and checksums; disclose conversion losses and deliberate arrangement changes. Common scores are optional. MIDI can describe notes but must not constrain native waveform/pitch tables, envelopes, modulation, filters, timing or voice dependencies. The generated `fuer-elise.melody.json` is an onset report retaining exact `frequencyWord` values, not an instrument program.

Keep editable recipes/workfiles with exported players; follow the owning workflow's conversion contract. A WAV or register dump alone is insufficient reusable instrument source.

Declare clock, chip model/count, addresses and update cadence. For reference playback, explicitly select the declared source clock; unknown or PAL/NTSC-capable declarations need a recorded experimental choice. Do not force NTSC as an international default. Composition portability means deliberate PAL and NTSC export targets with correct pitch, tempo and effect timing. The native workflow supports explicit PAL and NTSC targets, with PAL retained as the compatible default; effect tables run at target VBI rates and ADSR codes remain unchanged. The [PAL/NTSC portability requirement](docs/research/study-plan.md#required-palntsc-portability) separates NTSC reference rendering from composition/export support; never imply an NTSC render option makes a PAL standalone PRG portable. Account for shared filters, ring/sync dependencies, retriggering and modulation during release. Time-sharing percussion and bass on one voice can create additional instrument roles, but cannot preserve independent overlapping tails. Give dual SID deliberate musical roles. Choose effects through listening, including recorded rejected approaches.

## Learn mechanisms through execution

Follow the linked procedure: pin tune/profile/passage → execute from initialization → trace ordered SID writes and their executed code/tables → test a causal intervention → independently implement editable behavior → compare in context → transfer to another phrase.

Read interviews, manuals and commented sources alongside traces. Distinguish author statements, recovered code and inference. Captured-event replay does not prove an algorithm was understood. Register/code evidence explains programming; audio measurements support alignment, levels, clipping and endings. Remove superseded speculation.

Prefer verified headless VICE and file-monitor workflows. Use bridge tools only when actually connected. Instruction timestamps, checkpoints, frame snapshots and bus writes are different observations; separate bridge reads may resume execution between calls. Rendering does not prove speaker playback or listening.

## Listening and retained findings

For repeated build/render/comparison work, use the [recipe runner](docs/workflows/listening-package.md) and an owning checked-in recipe. Let it manage commands, deadlines, receipts, stage timings and the listening index. Reuse successful stages only after their declared input and output fingerprints match; include imported modules, tool binaries and data in recipe inputs. Change the recipe or fix a failed stage instead of manually recreating the pipeline. Musical judgments remain separate.

Use the [listening package](docs/workflows/audio-comparisons.md#package-a-listening-review): a representative phrase, a separate ending comparison and direct links to both full renders. Offer few labelled clips with actual filenames, A/B order and one clear question per judgment. Identify originals, muted diagnostics, independent recreations and hybrids. Match phrase/model/settings; retain original levels and record gains. Use common gain for contextual substitutions. Preserve shared audition files and stop iterating when asked to await feedback.

Present the reference alongside every generated reconstruction or A/B candidate. For genuinely new music, say explicitly that it is an original composition and identify the reused sounds; there is no original recording of that phrase. Link the source tune when it helps compare those sounds, clearly labelled as a timbral reference.

For short or repeated sounds, assess the attack, audible body, release and next retrigger in the intended mix. Clean gate gaps and healthy PCM do not establish natural articulation. Apply the [short-note ending guidance](docs/research/composition/sound-design-repertoire.md#shape-short-note-endings-in-context) when a sound is described as clipped, abrupt, ticking or drum-like. Distinguish relative improvement from acceptance of the sound’s musical role; a cleaner transient can remain unwanted or lack perceived body. Use a bounded subtraction comparison when voice attribution or the usefulness of an added part is uncertain. For intended audible changes, verify the submitted pair and actual signal contribution; a correct register trajectory does not establish audible body or a useful added role. When no difference is heard, diagnose before another audition and keep masking explanations provisional. Persist listening feedback as both a scoped case verdict and any supported reusable lesson, with retrieval links and editable examples where useful; do not promote an unaccepted parameter choice as a general solution.

Record the listener's verdict with its exact scope: perceptual agreement on one passage does not establish PCM identity, hardware equivalence or approval of another arrangement.

Before delegating listening judgments to a model, consult the [measured audio-assessment trials and bounded runners](docs/research/audio-assessment.md). Separate elementary perception, defect detection and musical preference: passing one does not qualify the others. Require identical-pair, known-difference, reversed-order and silence controls; fluent descriptions and high confidence do not establish audio perception. Freeze prompts and thresholds before testing a held-out passage. Preserve prompts, oracle-to-audio fingerprints, provider/model identity, responses and actual cost separately from human acceptance. Qwen's basic-category pass and SongBench's local Metal feasibility do not qualify either as a musical judge. The user confirms that model observations and scores remain experimental supporting signals until stronger task-specific evidence earns confidence; they must not determine musical acceptance or trigger arrangement changes on their own.

Apply the [standing model-assistance review rule](docs/research/audio-assessment.md#use-and-reassess-model-assistance) at the first representative audition, after listener feedback or a musical revision and before closing each musical case. Record the review in the owning study even when no model call is useful: state the reason and next checkpoint. Check changed model/prompt/preprocessing configurations before relying on them. Case closure requires these reviews to be accounted for, not successful model adoption. Keep this a small part of making music; no automatic paid calls, new service or optimization framework follows from a checkpoint.

Keep reusable mechanisms, constraints, provenance and reproduction instructions in one owning document; link from indexes. Retain acquired knowhow as searchable lookup tables and tested scripts/modules where those make the next task easier; documentation and reusable code complement each other. Promote repeatable probes into supported tools instead of requiring the next session to rediscover or rebuild them. Preserve full evidence in the format that retains its detail: structured traces, state snapshots, tables, code and audio as appropriate. Prose should explain and index that evidence, not replace it with a lossy summary. Preserve canonical analysis archives through [Git LFS and readable manifests](evidence/README.md); use ignored `build/` for working output. Follow the [public repository boundary](#public-repository-boundary) for original SIDs and reference WAVs, retaining source URLs and SHA-256 fingerprints in the download registry. No session diaries. Prefer searchable text/source; extract digital PDFs before OCR. Respect source redistribution limits. Promote instruments with editable parameters, purpose, target assumptions, demonstration, limitations and listening status.

This applies across the project, including preparation, validation, evidence capture and documentation generation. Give the automation explicit inputs, bounded execution, meaningful checks, retained diagnostics and concrete output paths. Use existing tools first; add the smallest missing orchestration. Agents should investigate unknowns, make decisions, review results and resolve failures; they should not remain the manual scheduler for an established procedure. Run the [automated build cleanup](docs/workflows/build-cache.md#automated-cleanup-and-when-to-run-it) after a substantial rendering/evidence batch once stable listening outputs and canonical evidence are retained, at musical-case closure, and before a session handoff that leaves substantial new build output. Stop writers to selected outputs first. Do not clean between rapid iterations that still need those cached stages; compacted/removed cache outputs must be regenerated. Report reclaimed bytes and remaining size. Do not repeatedly rerun cleanup merely because retained unique audio remains large, and do not retire listening samples or source assets to meet an arbitrary size target. Run this at the appropriate checkpoint without waiting for the user to notice disk growth.

## Choose sub-agent tiers by task

**Model tiers are symbolic (HIGH, MEDIUM, LOW).** Resolve only the active CLI's rows through the tier table in your global instructions; the maintainer's table is [Model tier mappings](https://github.com/mbackschat/coding-setup/blob/main/CLAUDE.md#model-tier-mappings). Keep model selectors and effort settings there. Report a missing or unsupported configuration instead of substituting. Start a fresh agent when selecting a different tier so a fork cannot silently retain the parent's model.

Delegation is authorized. Choose the least expensive suitable tier by the task's uncertainty and consequences, using these initial assignments rather than assuming measured equivalence between models:

| LOW | Check links and path references in named files; extract specified facts from existing receipts; summarize an existing verifier's result; apply an exact documentation correction; check a small documentation diff against explicit repository rules. | Supply the files, authoritative facts and pass/fail criteria. Use existing checkers for hashes and schemas. Return precise paths/lines and discrepancies; do not infer musical acceptance, select evidence for publication, change frozen provenance or repair an unfamiliar failure. |

Preserve CPU, VICE, rendered and listening evidence as separate claims. Bring unresolved cross-component assumptions to the coordinator. |
| HIGH | Resolve architecture or supported-contract tradeoffs; diagnose persistent model/CPU/VICE disagreements spanning components; review whether a verification design actually proves the intended musical/execution scope; integrate conflicting findings and audit completion. | State the consequential unresolved question and the evidence that will settle it. Use bounded delegates for separable work; keep integration and final claims with the coordinator. Human listening remains the authority for musical acceptance. |

For example, a reconstruction can assign a named sound component and its independent tests to MEDIUM, a check of the resulting documented paths/receipt fields to LOW, and a disagreement about initialization, timing or coverage to HIGH. Do not create this entire team automatically: keep small or tightly dependent work local, and do not duplicate work merely to use another tier.

Keep every assignment tied to the active deliverable or a concrete dependency it needs. Give minimal sufficient context, file ownership and acceptance criteria, including a stopping condition. Reuse informed agents when their tier still fits; batch related tasks and avoid duplicate research/testing. If a LOW task requires causal inference, unsupported assumptions or a substantive code change, return the evidence and hand it to MEDIUM instead of guessing. Escalate MEDIUM to HIGH for demonstrated cross-component difficulty or consequential uncertainty. Stop obsolete work. Follow the [automation rule](#automate-routine-execution): repeated established procedures belong in scripts or recipes, not a standing fleet of LOW agents.

## Choose validation that answers the question

This project permits judgment instead of mandatory red/green TDD everywhere. Define success and its oracle before implementation.

- **Reusable software/bugs:** prefer red/green guards covering meaningful behavior and the defect's mechanism.
- **Research:** use bounded experiments, instruction/register traces and independent execution; add focused tests when probes become tools.
- **Music:** verify exports/timing and listen in context; software checks cannot establish musical quality.
- **Documentation/configuration:** check links, parsing or a relevant smoke run; avoid artificial tests.

Verify register writes, timing, endings and binaries as appropriate. Preserve original sources and checksums; report conversion losses. Common scores must not constrain native SID expression. Label excerpts accurately.

Stock SID-Wizard Extra at tempo 1 initializes only the frequency high byte on a new note's first frame. ## Public Repository Boundary

Original project work is licensed under [MIT](LICENSE). Preserve the separate terms and attribution recorded in [third-party notices](THIRD_PARTY_NOTICES.md); the project license does not relicense upstream code, player binaries or musical sources.

Every sample song must have a public, reusable package under this two-tier policy:

- **Always include:** our tools and reusable instruments, recipes without embedded notes, source references and hashes. Link shared tools and instruments instead of duplicating them. This requirement covers every worked-on sample, including copyrighted songs and rejected experiments; preserve each sample's actual musical verdict and scope. Only include material we have the right to share; a recovered third-party program is not automatically ours.
- **Additionally, only for original, public-domain or appropriately licensed music:** include the complete score and SWM (SWS for two chips) plus a pinned export manifest, and provide playable SID/PRG files and WAV recordings, provided the particular source arrangement or edition and included player code also permit distribution. This native format applies to SID-Wizard songs; other backends retain their equivalent editable source and export metadata without claiming an SWM exists. Follow [the native source contract](docs/workflows/native-song-workflow.md#frozen-release-source-and-publication).

Check the [game-music permission review](docs/research/game-music-permissions.md) before classifying historical songs. A title-specific licence can permit a separately licensed sample alongside MIT tools; do not require every song to be MIT or public domain. The GPLv3 Rambo loader grant is scoped to the released loader, not its entire multi-subtune reference archive.

Before staging a sample package, record the composition and source-arrangement rights basis in its owning documentation, select the applicable tier and inspect the proposed files for embedded note sequences or equivalent encoded score data. Unknown rights use the always-included tier. Keep uncleared complete scores, native modules and generated song binaries/audio local under ignored output. Public URLs, attribution, hashes, file extensions and deterministic generation do not establish publication permission. Retain reviewed, distributable SID/PRG/WAV samples in [samples](samples/README.md), with source and output hashes, reproduction instructions and applicable notices. Use explicit `.gitignore` exceptions for those SID files; do not force-add reference binaries. The restriction on uncleared material must not be extended to rights-cleared project samples. This is a publication requirement, not a claim that all historical samples have already been audited or packaged. Legacy tracked reconstructions, including `songs/flashdance-decoded.json` and `songs/shades-score.json`, contain musical note data and need a rights review before further publication; the policy change alone does not clear them.

Keep original reference SID binaries out of the public repository, including history and LFS. Record each source URL and SHA-256 fingerprint in [the asset registry](config/local-assets.json); use [the verified downloader](scripts/setup-project.py) on demand. Keep reference WAVs out of Git under ignored `.local/` or `build/`; document exact reproduction commands, source hashes, subtune, renderer/version/settings, duration, gain, trim points and output hashes. Analysis artifacts, traces, lookup tables, editable descriptions and reusable code may be tracked when useful. Preserve complete evidence alongside concise prose, with source hashes, settings and reproduction commands. Downloaded skills retain the ignored `skills/<name>/` installation layout. Never force-add original SID files; check tracked files and history before publishing.
